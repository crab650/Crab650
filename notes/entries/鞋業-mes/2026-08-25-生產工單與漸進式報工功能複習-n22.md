# 2026-08-25 生產工單與漸進式報工功能複習

這份筆記記錄今天將 `03.openmes-production-execution-demo` 從最小流程升級成較完整 MES 生產執行 Demo 的過程，供日後複習設計原因與操作規則。

## 一、今天完成的功能

### 1. 工單草稿與發布

原本建立工單後立即產生快照與 Batch，不容易修正。現在改為：

```text
建立工單 → DRAFT
修改及確認產品、產線、數量、交期
        ↓
發布工單 → RELEASED
        ↓
凍結製程與 BOM
```

設計重點：

- 草稿可以修改。
- 發布後才視為正式生產指示。
- 發布時重新確認產品版本仍有效。
- 發布時檢查產線是否具備該產品能力。
- 發布後的快照不受 `02` 主檔後續修改影響。

### 2. 完整工單生命週期

新增：

- `DRAFT`：草稿
- `RELEASED`：已發布
- `PAUSED`：暫停
- `COMPLETED`：生產完成
- `CANCELLED`：取消
- `CLOSED`：結案

規則：

- 已發布工單可以暫停。
- 暫停時不能開工或報工。
- 恢復後才能繼續。
- 取消必須填寫原因。
- 已經開始報工的工單不可直接取消，避免破壞交易歷史。
- 完成後可以結案。
- 每次生命週期改變都保存歷程。

### 3. 多 Batch 拆分

一張工單不再只有一個自動 Batch，可以依實務拆分：

```text
工單 WO-001，計畫 1,000 雙
├── Batch 1：BLACK / 40 / 300
├── Batch 2：BLACK / 41 / 300
└── Batch 3：WHITE / 42 / 400
```

每個 Batch 可以輸入：

- 數量
- 顏色
- 尺碼
- 批號

核心守恆：

```text
所有有效 Batch 數量加總 ≤ 工單計畫數量
```

只有尚未開工的 Batch 可以刪除。

### 4. 逐次報工

報工不再直接覆寫工序數量，而是每次建立一筆交易：

```text
裁斷投入 300

08:00 報良品 100
10:00 報良品 80、不良 5
13:00 報良品 110、不良 5

累計良品 290
累計不良 10
總投入 300
```

這樣可以回答：

- 什麼時間報了多少？
- 是誰報的？
- 每次有哪些不良？
- 哪一筆報工造成數量變化？

### 5. 漸進式站間流轉

今天最重要的修正，是從「上一站全部完成才解鎖下一站」改成流水線式流轉。

舊邏輯：

```text
裁斷 300 全部完成
        ↓
針車才可開工
```

新邏輯：

```text
裁斷先完成良品 100
        ↓
針車立即 READY，可先接 100

裁斷再完成良品 80
        ↓
針車可投入量增加到累計 180
```

這比較符合鞋廠流水生產：不同工序可以同時進行，但後站永遠不能超過前站已產出的良品。

公式：

```text
下一站投入上限 = 上一站累計良品
下一站目前可報 = 上一站累計良品 - 下一站累計良品 - 下一站累計不良
```

第一站：

```text
第一站投入上限 = Batch 目標數量
```

### 6. 一筆報工多個不良

原本一筆報工只能選一種不良代碼，無法表示同時發生多種問題。

現在畫面可以按「＋增加不良項目」：

```text
本次良品：90

本次不良明細：
├── 開線：6
├── 髒污：3
└── 色差：1
```

系統保存：

```text
報工表頭：良品 90、不良合計 10
不良子表：開線 6、髒污 3、色差 1
```

同一筆報工不能重複使用相同的不良代碼。

## 二、完整操作練習

### 步驟 1：在 `02` 準備主檔

確認已有：

1. 啟用的產品類型。
2. 已發布的產品版本。
3. 有效製程範本與製程步驟。
4. 已發布 BOM。
5. 啟用的生產線。
6. `line_product_type` 已指定該產線能生產此產品。
7. 不良代碼。

### 步驟 2：建立草稿工單

輸入：

- 工單號
- 產品版本
- 生產線
- 計畫數量
- 優先順序
- 交期

儲存後狀態為 `DRAFT`。

### 步驟 3：發布工單

按「發布並凍結」。系統會：

1. 驗證產品版本。
2. 驗證產線能力。
3. 取得製程範本與步驟。
4. 取得已發布 BOM。
5. 建立製程快照與 BOM 快照。
6. 將工單改為 `RELEASED`。

### 步驟 4：拆分 Batch

例如工單數量 600：

```text
Batch 1：BLACK / 40 / 300
Batch 2：WHITE / 41 / 300
```

每建立一個 Batch，系統從工單製程快照展開自己的工序。

### 步驟 5：第一站開工與部分報工

Batch 1 第一站裁斷開工，投入 300。

第一次只報：

```text
本次良品：100
```

結果：

- 裁斷保持 `IN_PROGRESS`。
- 裁斷累計良品為 100。
- 針車立即變成 `READY`。
- 針車可投入量為 100。

### 步驟 6：下一站並行生產

針車可以先開工並報 60：

```text
針車投入上限：100
針車本次良品：60
針車尚可報：40
```

此時裁斷仍可以繼續報工，兩站同時進行。

### 步驟 7：登記多種不良

裁斷下一次報工：

```text
本次良品：75
開線：3
髒污：2
```

本次總數為 80，報工歷史會保存一筆表頭和兩筆不良明細。

### 步驟 8：完成與結案

當：

1. 所有計畫數量都已拆成 Batch。
2. 每個 Batch 最後一道工序都完成。

工單會自動成為 `COMPLETED`，之後可按「結案」成為 `CLOSED`。

## 三、今天修正的錯誤與學習點

### 1. Jinja 空表單欄位錯誤

錯誤：

```text
ImmutableMultiDict object has no attribute 'product_revision_id'
```

原因：第一次 GET 建立頁面時表單是空的，模板卻直接用屬性讀取不存在欄位。

修正：

- Route 將 SQLite Row 或 `request.form` 統一轉成普通 `dict`。
- Jinja 使用 `form_values.get('field', default)`。

學習：模板不應假設使用者表單一定包含所有欄位。

### 2. 第一次報工自動填滿剩餘量

原本良品欄預填全部剩餘量，使用者直接送出就會完成整道工序，造成「不能報第二筆」的錯覺。

修正：

- 良品欄改為空白。
- Placeholder 顯示目前可報數量。
- 使用者輸入的是「本次數量」，不是累計數量。

### 3. 下一工序解鎖太晚

原本只有上一工序 `DONE` 才將下一站改為 `READY`。

修正：只要上一站累計良品大於 0，下一站即可 `READY`；但下一站完成仍須等待上一站最終數量確定。

### 4. 既有資料需要回填

程式修正後，舊資料中已經有 100 良品、下一站卻仍是 `PENDING`。

Migration 103 負責將這些既有下一站改為 `READY`。這提醒我們：

> 改程式邏輯不等於舊資料會自動符合新規則，必要時要做資料 migration。

## 四、Migration 複習

| 版本 | 今天的用途 |
|---|---|
| `100` | 最初工單、快照、Batch、批次工序 |
| `101` | 工單生命週期、多 Batch、逐次報工、狀態歷程 |
| `102` | 多不良明細子表 |
| `103` | 舊資料漸進式解鎖回填 |

每個 migration 只由 `03` 管理，不修改 `02` 擁有的主檔結構。

## 五、測試覆蓋

目前自動測試涵蓋：

- 登入與頁面存取。
- 草稿修改、發布與快照。
- 多 Batch 與分批總量限制。
- 同工序多次報工累加。
- 前站部分良品立即解鎖後站。
- 不良必須有有效代碼。
- 一筆報工多個不良明細。
- 上一站良品成為下一站投入上限。
- 暫停後禁止報工，恢復後可繼續。
- 取消原因及取消限制。
- 完整生產後自動完成並可結案。

測試使用共用 DB 的暫存副本，不會污染實際練習資料。

## 六、複習問題

1. 為什麼工單需要草稿與發布兩個階段？
2. 為什麼要保存製程及 BOM 快照，不能只保留主檔外鍵？
3. `work_orders.status` 和 `lifecycle_status` 有什麼不同？
4. 為什麼報工要新增交易紀錄，而不是直接修改累計數量？
5. 下一站投入上限應如何計算？
6. 為什麼下一站可以在上一站尚未 `DONE` 時開工？
7. 下一站已報完目前可用量時，為什麼不能立刻判定最終完成？
8. 一筆報工為什麼需要表頭和不良明細子表？
9. 為什麼已經報工的工單不能直接取消？
10. 修改流程邏輯後，為什麼可能還需要資料回填 migration？

## 七、下一步可練習方向

建議依序延伸：

1. 報工更正與沖銷，不直接刪除歷史交易。
2. 不良處置：報廢、返工、待判、特採。
3. 返工工序與重新投入數量。
4. BOM 領料與實際扣料。
5. 物料批號與成品批次追溯。
6. 工單預計開始／完成與簡易排程。
7. 停機原因、設備事件與 OEE。
