# Flask 測試隔離：學習指南與實作範例

## 1. 學習目標

完成本指南後，你將能理解並實作：

1. 為什麼自動測試不能直接使用正式資料庫。
2. 如何讓每個測試使用獨立的臨時 SQLite 資料庫。
3. 如何使用 Flask Application Factory 切換正式與測試設定。
4. 如何用 Flask Test Client 測試 API 和網頁。
5. 如何模擬登入 Session，讓測試專注於業務功能。
6. 如何證明測試執行後沒有污染正式資料。
7. 單元測試、整合測試與正式環境驗收的差異。

## 2. 我們要建立的範例

建立一個很小的「出貨申請」系統：

- `POST /api/shipments`：建立出貨申請。
- `GET /api/shipments`：查詢所有申請。
- `GET /shipments`：登入後才能觀看的網頁。
- 正常啟動時使用 `instance/app.db`。
- 自動測試時使用隨機臨時目錄中的 `test.db`。
- 測試結束後，臨時資料庫自動刪除。

建議練習目錄：

```text
flask-test-learning/
├─ app.py
├─ test_app.py
└─ requirements.txt
```

## 4. 建立可測試的 Flask 應用

建立 `app.py`：

```python
import sqlite3
from pathlib import Path

from flask import Flask, current_app, g, jsonify, request, session


def get_db() -> sqlite3.Connection:
    """同一個 Request 只建立一個資料庫連線。"""
    if "db" not in g:
        g.db = sqlite3.connect(current_app.config["DATABASE"])
        g.db.row_factory = sqlite3.Row
    return g.db


def close_db(exception=None) -> None:
    database = g.pop("db", None)
    if database is not None:
        database.close()


def init_db() -> None:
    database = get_db()
    database.execute(
        """
        CREATE TABLE IF NOT EXISTS shipments (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            shipment_no TEXT NOT NULL UNIQUE,
            status TEXT NOT NULL
        )
        """
    )
    database.commit()


def create_app(test_config: dict | None = None) -> Flask:
    """Application Factory：每次呼叫都能建立一個獨立 App。"""
    app = Flask(__name__, instance_relative_config=True)

    # 正常環境的預設設定。
    app.config.from_mapping(
        SECRET_KEY="development-secret",
        DATABASE=str(Path(app.instance_path) / "app.db"),
        TESTING=False,
    )

    # 測試可以覆寫 DATABASE、SECRET_KEY、TESTING 等設定。
    if test_config:
        app.config.update(test_config)

    Path(app.config["DATABASE"]).parent.mkdir(parents=True, exist_ok=True)
    app.teardown_appcontext(close_db)

    with app.app_context():
        init_db()

    @app.post("/api/shipments")
    def create_shipment():
        body = request.get_json(silent=True) or {}
        shipment_no = str(body.get("shipmentNo") or "").strip()
        if not shipment_no:
            return jsonify({"message": "shipmentNo is required"}), 400

        database = get_db()
        try:
            cursor = database.execute(
                "INSERT INTO shipments (shipment_no, status) VALUES (?, ?)",
                (shipment_no, "PREPARED"),
            )
            database.commit()
        except sqlite3.IntegrityError:
            return jsonify({"message": "shipmentNo already exists"}), 409

        return jsonify({
            "id": cursor.lastrowid,
            "shipmentNo": shipment_no,
            "status": "PREPARED",
        }), 201

    @app.get("/api/shipments")
    def list_shipments():
        rows = get_db().execute(
            "SELECT id, shipment_no, status FROM shipments ORDER BY id"
        ).fetchall()
        return jsonify([
            {
                "id": row["id"],
                "shipmentNo": row["shipment_no"],
                "status": row["status"],
            }
            for row in rows
        ])

    @app.get("/shipments")
    def shipment_page():
        if not session.get("user_id"):
            return "Login required", 401
        return f"Welcome {session.get('display_name', 'User')}"

    return app


if __name__ == "__main__":
    create_app().run(debug=True)
```

### 這段程式最重要的設計

`create_app()` 沒有把資料庫路徑寫死。正式啟動可以使用預設的 `instance/app.db`，測試則能傳入另一個路徑：

```python
create_app({"DATABASE": "其他資料庫路徑"})
```

這就是測試隔離的基礎。如果程式在模組載入時直接連上正式資料庫，測試便很難安全替換連線。

## 5. 建立隔離測試

建立 `test_app.py`：

```python
import tempfile
import unittest
from pathlib import Path

from app import create_app


class ShipmentAppTest(unittest.TestCase):
    def setUp(self):
        # 每一個測試方法執行前，都建立新的臨時目錄。
        self.temp_dir = tempfile.TemporaryDirectory()
        self.db_path = Path(self.temp_dir.name) / "test.db"

        self.app = create_app({
            "TESTING": True,
            "SECRET_KEY": "test-secret",
            "DATABASE": str(self.db_path),
        })
        self.client = self.app.test_client()

    def tearDown(self):
        # 每一個測試方法完成後，刪除資料庫及臨時目錄。
        self.temp_dir.cleanup()

    def login(self):
        with self.client.session_transaction() as browser_session:
            browser_session["user_id"] = 1
            browser_session["username"] = "TEST001"
            browser_session["display_name"] = "Test User"

    def test_create_and_query_shipment(self):
        created = self.client.post(
            "/api/shipments",
            json={"shipmentNo": "SSS-TEST-001"},
        )
        self.assertEqual(created.status_code, 201)
        self.assertEqual(created.get_json()["status"], "PREPARED")

        result = self.client.get("/api/shipments")
        self.assertEqual(result.status_code, 200)
        self.assertEqual(len(result.get_json()), 1)
        self.assertEqual(result.get_json()[0]["shipmentNo"], "SSS-TEST-001")

    def test_duplicate_shipment_is_rejected(self):
        payload = {"shipmentNo": "SSS-TEST-001"}
        first = self.client.post("/api/shipments", json=payload)
        second = self.client.post("/api/shipments", json=payload)

        self.assertEqual(first.status_code, 201)
        self.assertEqual(second.status_code, 409)

    def test_protected_page_requires_login(self):
        response = self.client.get("/shipments")
        self.assertEqual(response.status_code, 401)

    def test_session_can_simulate_login(self):
        self.login()
        response = self.client.get("/shipments")

        self.assertEqual(response.status_code, 200)
        self.assertIn("Test User", response.get_data(as_text=True))

    def test_database_is_created_inside_temporary_directory(self):
        self.assertTrue(self.db_path.exists())
        self.assertEqual(self.db_path.parent, Path(self.temp_dir.name))


if __name__ == "__main__":
    unittest.main()
```

執行測試：

```powershell
python -m unittest -v
```

預期結果：

```text
Ran 5 tests

OK
```

## 6. 為什麼每個測試都不會互相污染？

`unittest` 會針對每個 `test_...` 方法重新執行一次：

```text
setUp
  └─ test_create_and_query_shipment
tearDown

setUp
  └─ test_duplicate_shipment_is_rejected
tearDown
```

每次 `setUp()` 都產生不同的隨機目錄：

```text
Temp/tmp_a123/test.db
Temp/tmp_b456/test.db
```

所以第一個測試建立的 `SSS-TEST-001` 不會存在於第二個測試中。第二個測試若需要資料，必須自行安排測試資料。這個特性稱為「測試獨立性」。

## 7. Flask Test Client 是什麼？

以下程式：

```python
self.client.post("/api/shipments", json=payload)
```

會經過真正的 Flask Routing、Request Parsing 和 Response Handling，但不會啟動真正的 HTTP Server，也不會使用公司網路。

它適合驗證：

- URL 是否正確。
- HTTP Method 是否正確。
- JSON 驗證是否正確。
- HTTP Status Code 是否正確。
- 寫入及讀取資料是否正確。
- 登入保護是否生效。

它不能證明：

- IIS、Nginx 或防火牆設定正確。
- SIF 能透過實際網路連到 IEMS。
- 正式環境 API Key 正確。
- Vue 畫面在瀏覽器中的操作完全正常。

## 8. Session 模擬不是關閉權限

以下寫法：

```python
with self.client.session_transaction() as browser_session:
    browser_session["user_id"] = 1
```

只是在測試瀏覽器的 Cookie Session 中放入登入資料。正式程式的權限檢查仍然存在。

建議至少保留兩種測試：

1. 未登入時應被拒絕。
2. 模擬登入後應能進入。

如果要測試真正的登入功能，應另外建立登入測試，走完整帳號、密碼與雜湊驗證；不要讓所有業務功能測試都重複登入流程。

## 9. 測試資料設計原則

### Arrange、Act、Assert

每個測試可以分成三個階段：

```python
def test_example(self):
    # Arrange：準備輸入及前置資料
    payload = {"shipmentNo": "SSS-TEST-001"}

    # Act：執行要測試的功能
    response = self.client.post("/api/shipments", json=payload)

    # Assert：驗證可以觀察到的結果
    self.assertEqual(response.status_code, 201)
```

### 一個測試只說明一個主要行為

好的名稱：

```text
test_duplicate_shipment_is_rejected
test_rejected_order_requires_reason
test_completed_batch_can_be_pulled_by_sif
```

不清楚的名稱：

```text
test_1
test_everything
test_api
```

### 不要依賴執行順序

錯誤觀念：第二個測試使用第一個測試建立的資料。

正確方式：每個測試自行準備需要的資料，無論單獨執行或交換順序都應通過。

## 10. `:memory:` 與臨時檔案怎麼選？

SQLite 也支援：

```python
"DATABASE": ":memory:"
```

但初學及 Flask 專案較推薦臨時檔案，原因是 SQLite 的記憶體資料庫通常只存在於單一 Connection。若應用程式關閉原連線、下一個 Request 建立新連線，資料可能消失。

| 方式 | 優點 | 注意事項 |
|---|---|---|
| 臨時 `test.db` | 行為接近正式 SQLite、容易除錯 | 比純記憶體稍慢 |
| `:memory:` | 很快、不產生檔案 | 多 Connection 時容易得到不同資料庫 |

目前 IEMS 使用臨時 SQLite 檔案，是穩定且容易理解的選擇。

## 11. 如何證明沒有碰到正式資料庫？

可以加入三項保護：

### 保護一：測試必須開啟 `TESTING`

```python
assert self.app.config["TESTING"] is True
```

### 保護二：測試路徑必須位於臨時目錄

```python
assert Path(self.app.config["DATABASE"]).parent == Path(self.temp_dir.name)
```

### 保護三：拒絕已知正式路徑

```python
database_path = Path(self.app.config["DATABASE"]).resolve()
production_path = Path("instance/iems_mock.db").resolve()
assert database_path != production_path
```

這些 Assertion 應放在 `setUp()`，讓設定錯誤時立即停止測試。

## 12. 單元測試、整合測試與驗收測試

| 測試層級 | 使用環境 | 主要目的 |
|---|---|---|
| 隔離功能測試 | Flask Test Client + 臨時 SQLite | 快速驗證程式邏輯 |
| 系統整合測試 | 測試版 SIF API + IEMS + SQL Server | 驗證跨系統通訊與資料寫入 |
| 使用者驗收測試 | 瀏覽器操作測試環境 | 驗證實際操作流程與畫面 |

三者不能互相取代。比較安全的順序是：

```text
隔離功能測試
    ↓
測試環境整合測試
    ↓
使用者驗收
    ↓
正式部署
```

## 13. 對照目前 IEMS 專案

目前 IEMS 已使用相同架構：

- 應用程式工廠：`OutPageTest/IEMS/app.py` 的 `create_app()`。
- 隔離測試：`OutPageTest/IEMS/tests/test_export_api.py`。
- 臨時目錄：`tempfile.TemporaryDirectory()`。
- 測試資料庫：臨時目錄內的 `test.db`。
- 模擬登入：`client.session_transaction()`。
- API 呼叫：Flask `test_client()`。

目前自動測試涵蓋的實際案例包括：

- API Key 必填。
- Idempotency 重送。
- 相同 Key、不同 Payload 衝突。
- 每個 SO 獨立審核。
- 駁回時建議日期及原因必填。
- 所有 SO 完成後才提供完整結果。
- SIF 拉取結果並 ACK。
- SO 駁回重送後顯示 Round 1、Round 2 歷程。

閱讀順序建議：

1. 先看測試檔的 `setUp()`、`tearDown()` 和 `login()`。
2. 選一個名稱容易理解的測試案例。
3. 找出該案例呼叫的 URL。
4. 回到 `app.py` 找相對應 Route。
5. 在測試中故意改錯一個預期值，觀察測試如何失敗。
6. 還原後重新執行，確認測試恢復通過。

## 14. 建議練習

### 練習一：必填驗證

新增測試：未傳 `shipmentNo` 時應回傳 HTTP 400。

### 練習二：確認初始資料隔離

在測試開始時呼叫 `GET /api/shipments`，驗證回傳空陣列。

### 練習三：增加取消功能

新增：

```text
POST /api/shipments/<id>/cancel
```

並測試狀態從 `PREPARED` 變成 `CANCELLED`。

### 練習四：權限測試

讓取消功能要求登入，再分別測試：

- 未登入回傳 401。
- 模擬登入後取消成功。

### 練習五：測試不允許重複取消

第一次取消成功，第二次取消應回傳 409。

## 15. 常見錯誤

### 測試連到正式資料庫

原因通常是忘記傳入測試設定，或程式在 `create_app()` 之外就建立資料庫連線。

### 測試單獨執行成功，一起執行失敗

通常表示不同測試共用了資料或全域狀態。

### 測試結束後無法刪除 SQLite 檔案

Windows 常見原因是資料庫 Connection 尚未關閉。確認已註冊 `teardown_appcontext(close_db)`，也不要把 Connection 儲存在全域變數。

### 只檢查 HTTP 200

HTTP 200 不代表資料正確。還要驗證 Response Body、資料庫狀態與重要欄位。

### 用 Session 模擬取代所有登入測試

Session 模擬適合隔離業務測試，但登入功能本身仍需獨立測試。

### 測試中呼叫正式外部 API

隔離測試不應真正傳送資料給 SIF、MES、Email 或其他系統。外部連線應改用 Fake、Mock 或專用測試環境。
