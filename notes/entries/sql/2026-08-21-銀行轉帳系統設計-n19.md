# 銀行轉帳系統設計學習筆記

## 1. 學習目標

這份文件用一個簡化的「銀行帳戶轉帳系統」理解金融系統最重要的資料庫與帳務概念。

核心學習路線：

```text
Transaction
    ↓
ACID
    ↓
Concurrency
    ↓
Idempotency
    ↓
Ledger
    ↓
Double Entry
    ↓
Reconciliation
```

完成後應該能理解：

* 為什麼轉帳不能只是兩個 `UPDATE`
* 為什麼資料庫 Transaction 很重要
* 多人同時操作會發生什麼問題
* 為什麼 API 重送不能造成重複扣款
* Balance 與 Ledger 有什麼不同
* 為什麼金融系統使用複式帳本
* 銀行為什麼需要每天對帳

---

# 2. 最基本的銀行帳戶模型

假設銀行只有兩個客戶：

| Account | Name   | Balance |
| ------- | ------ | ------: |
| A001    | User A |   1,000 |
| B001    | User B |     500 |

現在：

```text
A001 → B001
轉帳 200 元
```

完成後：

| Account | Balance |
| ------- | ------: |
| A001    |     800 |
| B001    |     700 |

從最簡單的角度來看，轉帳其實就是：

```text
A001 -200
B001 +200
```

概念上與 ERP 的庫存調撥很像：

```text
倉庫 A -20 PCS
倉庫 B +20 PCS
```

但是金融系統不能只考慮「正常情況」。

還必須處理：

* 執行到一半失敗
* 同時轉帳
* 重複送出
* 餘額不足
* Server 當機
* 資料異常
* 帳務不平
* 外部系統資料不一致

因此需要下面這些機制。

---

# 3. Transaction：交易

## 3.1 問題

假設程式依序執行：

```sql
UPDATE account
SET balance = balance - 200
WHERE account_id = 'A001';

UPDATE account
SET balance = balance + 200
WHERE account_id = 'B001';
```

第一行成功：

```text
A001：1000 → 800
```

但是第二行執行時 Server 發生錯誤。

結果：

```text
A001 = 800
B001 = 500
```

200 元憑空消失。

---

## 3.2 解決方法：Database Transaction

```sql
BEGIN TRANSACTION;

UPDATE account
SET balance = balance - 200
WHERE account_id = 'A001';

UPDATE account
SET balance = balance + 200
WHERE account_id = 'B001';

COMMIT;
```

如果中間發生錯誤：

```sql
ROLLBACK;
```

資料回到：

```text
A001 = 1000
B001 = 500
```

### 核心概念

> 一筆業務交易中的多個資料庫操作，要嘛全部成功，要嘛全部失敗。

---

# 4. ACID：可靠 Transaction 的四個特性

ACID 是資料庫 Transaction 的核心概念。

## A — Atomicity 原子性

轉帳包含：

```text
A -200
B +200
```

不能只成功一半。

只能：

```text
全部成功
```

或者：

```text
全部失敗
```

---

## C — Consistency 一致性

轉帳之前：

```text
A = 1000
B = 500

Total = 1500
```

轉帳之後：

```text
A = 800
B = 700

Total = 1500
```

系統必須從一個合法狀態進入另一個合法狀態。

---

## I — Isolation 隔離性

如果很多人同時轉帳：

```text
Transaction A
Transaction B
Transaction C
```

不能因為同時讀寫相同資料而產生錯誤結果。

這會帶到下一章的：

**Concurrency Control。**

---

## D — Durability 持久性

一旦：

```sql
COMMIT;
```

成功，就代表交易已經正式成立。

即使下一秒：

```text
Server Restart
Power Failure
Application Crash
```

已提交的資料也不能憑空消失。

---

# 5. Concurrency：並發控制

這是金融系統非常重要的問題。

假設：

```text
A001 Balance = 1000
```

同一瞬間收到：

```text
Request 1
A → B 800

Request 2
A → C 800
```

兩個程式同時查：

```sql
SELECT balance
FROM account
WHERE account_id = 'A001';
```

兩邊都得到：

```text
1000
```

所以：

```text
Request 1：
1000 >= 800
PASS

Request 2：
1000 >= 800
PASS
```

但實際上 A 根本沒有 1600 元。

這是一種：

**Race Condition（競爭條件）**

---

## 5.1 Atomic Update

其中一種做法：

```sql
UPDATE account
SET balance = balance - 800
WHERE account_id = 'A001'
AND balance >= 800;
```

然後檢查：

```text
Affected Rows
```

第一次：

```text
1000 >= 800

更新成功
Balance = 200
Affected Rows = 1
```

第二次：

```text
200 >= 800

條件不成立
Affected Rows = 0
```

第二筆交易因此拒絕。

---

## 5.2 更進階的並發控制

正式系統還可能使用：

* Row Lock
* Pessimistic Lock
* Optimistic Lock
* Isolation Level
* Version Number
* Serializable Transaction

這些技術的目的基本相同：

> 多個交易同時操作資料時，仍然必須得到正確結果。

---

# 6. Idempotency：冪等性

假設使用者按：

```text
轉帳 200
```

App 發送：

```text
POST /transfer
```

Server 已經成功完成：

```text
A -200
B +200
```

但是 Response 在網路中斷掉。

App 不知道到底成功沒有。

所以重新發送一次：

```text
POST /transfer
```

如果 Server 沒有防護：

```text
第一次 -200
第二次 -200
```

最後變成轉帳 400。

---

## 6.1 Idempotency Key

每一次轉帳產生唯一 ID：

```text
TX202608210001
```

Request：

```json
{
  "transaction_id": "TX202608210001",
  "from_account": "A001",
  "to_account": "B001",
  "amount": 200
}
```

Server 收到後先檢查：

```sql
SELECT *
FROM transfer
WHERE transaction_id = 'TX202608210001';
```

如果不存在：

```text
執行轉帳
```

如果已經存在：

```text
不要重新執行
回傳原來的交易結果
```

因此：

```text
同一個 Request 發送 1 次 → 轉帳一次

同一個 Request 發送 10 次 → 還是只轉帳一次
```

這就是 Idempotency。

---

# 7. Ledger：交易帳本

只保存 Balance 是不夠的。

假設資料庫只有：

| Account | Balance |
| ------- | ------: |
| A001    |     800 |
| B001    |     700 |

我們知道 A 有 800 元。

但是不知道：

> 為什麼是 800？

因此需要：

**Ledger（帳本）**

例如：

| Transaction | Account | Amount | Description        |
| ----------- | ------- | -----: | ------------------ |
| TX001       | A001    |   -200 | Transfer to B001   |
| TX001       | B001    |   +200 | Transfer from A001 |

這代表：

```text
TX001

A001 -200
B001 +200
```

---

## 7.1 Balance 與 Ledger 的差別

### Balance

回答：

> 現在有多少錢？

```text
A001 = 800
```

### Ledger

回答：

> 為什麼現在有 800？

例如：

```text
Opening Balance    +1000
Transfer TX001      -200
------------------------
Current Balance      800
```

所以：

```text
Balance = 現在的結果

Ledger = 造成這個結果的完整歷史
```

金融系統真正重要的是 **Ledger**。

---

# 8. Double Entry：複式帳本

接下來進入會計思想。

A 轉 200 給 B：

```text
A001 -200
B001 +200
```

一筆交易產生兩個 Ledger Entry。

```text
TX001
----------------
A001      -200
B001      +200
----------------
TOTAL        0
```

因此可以建立一個重要規則：

```text
SUM(Ledger Entries) = 0
```

---

## 8.1 如果系統發生錯誤

假設：

```text
A001 -200
B001 +190
```

檢查：

```text
-200 + 190 = -10
```

不等於：

```text
0
```

立刻知道：

> 這筆帳不平。

因此 Double Entry 不只是會計概念。

它也是非常強的：

**Data Integrity Control**

---

# 9. Reconciliation：對帳

即使前面全部做好，金融系統還需要定期檢查：

> 不同資料來源是不是一致？

這就是：

**Reconciliation（對帳）**

---

## 9.1 Balance vs Ledger

Account Table：

```text
A001 Balance = 800
```

Ledger：

```text
Opening Balance   1000
TX001             -200
----------------------
Calculated          800
```

比較：

```text
Account Balance = 800
Ledger Balance  = 800

PASS
```

---

如果：

```text
Account Balance = 750
Ledger Balance  = 800
```

則：

```text
Difference = -50
```

系統必須產生異常：

```text
RECONCILIATION FAILED
```

並調查這 50 元差異從哪裡來。

---

# 10. 完整轉帳流程

現在把所有概念組合起來。

```text
使用者
   │
   │ A → B 200
   ▼
Transfer API
   │
   │ transaction_id = TX001
   ▼
┌────────────────────────────┐
│ ① Idempotency Check        │
│ TX001 是否已經執行？       │
└─────────────┬──────────────┘
              │
              ▼
       BEGIN TRANSACTION
              │
              ▼
┌────────────────────────────┐
│ ② Concurrency Control      │
│ 檢查並鎖定/原子更新 A      │
└─────────────┬──────────────┘
              │
              ▼
┌────────────────────────────┐
│ ③ Balance Check            │
│ A 是否有足夠餘額？         │
└─────────────┬──────────────┘
              │
              ▼
┌────────────────────────────┐
│ ④ Ledger                   │
│ A -200                     │
│ B +200                     │
└─────────────┬──────────────┘
              │
              ▼
┌────────────────────────────┐
│ ⑤ Double Entry Check       │
│ -200 + 200 = 0             │
└─────────────┬──────────────┘
              │
              ▼
┌────────────────────────────┐
│ ⑥ Update Balance           │
│ A = 800                    │
│ B = 700                    │
└─────────────┬──────────────┘
              │
              ▼
            COMMIT
              │
              ▼
           SUCCESS
```

之後另外執行：

```text
Reconciliation Job
        │
        ├── Account Balance
        │
        └── Ledger Balance
                 │
                 ▼
              Compare
                 │
          ┌──────┴──────┐
          │             │
        Match        Mismatch
          │             │
          ▼             ▼
         OK          Alert
```

# 12. 一筆交易在四張表中的關係

例如：

```text
A001 → B001
200 元
TX001
```

### Transfer

```text
TX001
A001
B001
200
SUCCESS
```

### Ledger

```text
TX001 | A001 | -200
TX001 | B001 | +200
```

### Account

```text
A001 | 800
B001 | 700
```

### Reconciliation

```text
A001 | Account=800 | Ledger=800 | PASS
B001 | Account=700 | Ledger=700 | PASS
```

因此可以把資料模型理解成：

```text
                 Transfer
                    │
                    │ TX001
                    ▼
            ┌───────────────┐
            │    Ledger     │
            ├───────────────┤
            │ A001   -200   │
            │ B001   +200   │
            └───────────────┘
               │         │
               ▼         ▼
            Account    Account
             A001       B001
              800        700
               │         │
               └────┬────┘
                    ▼
             Reconciliation
```

# 13. 與 ERP 庫存系統對照

銀行系統和 ERP 庫存其實有很多相似之處：

| 銀行系統                 | ERP 庫存                               |
| -------------------- | ------------------------------------ |
| Account              | Warehouse                            |
| Balance              | On-hand Qty                          |
| Money                | Material                             |
| Transfer             | Stock Transfer                       |
| Ledger               | Inventory Transaction                |
| Debit / Credit       | Issue / Receipt                      |
| Insufficient Balance | Insufficient Stock                   |
| Transaction ID       | Document No.                         |
| Reconciliation       | Inventory Reconciliation             |
| Bank Statement       | Physical Inventory / External Record |

例如：

```text
銀行：

Account A -200
Account B +200
```

與：

```text
ERP：

Warehouse A -20
Warehouse B +20
```

在資訊系統設計思想上非常接近。

# 14. 真正需要學會的核心

不要把「轉帳系統」理解成：

```text
UPDATE A -200
UPDATE B +200
```

而應該理解成：

```text
                 Transfer
                    │
                    ▼
              Transaction
                    │
                    ▼
                  ACID
                    │
                    ▼
             Concurrency
                    │
                    ▼
             Idempotency
                    │
                    ▼
                 Ledger
                    │
                    ▼
              Double Entry
                    │
                    ▼
            Reconciliation
```

其中每一層都在解決不同問題：

| 技術             | 解決的問題        |
| -------------- | ------------ |
| Transaction    | 做到一半失敗       |
| ACID           | 保證交易可靠性      |
| Concurrency    | 多人同時操作       |
| Idempotency    | Request 重複執行 |
| Ledger         | 保留完整帳務歷史     |
| Double Entry   | 保證資金來源與去向平衡  |
| Reconciliation | 找出系統之間的資料差異  |

---

# 15. 最重要的一句話

銀行轉帳的基本動作並不複雜：

```text
A 扣款
B 入帳
```

真正困難的是：

> **無論斷線、重送、多人同時操作、Server 當機或資料異常，都不能讓錢多出來、消失、重複扣款或無法追查。**

所以金融系統真正的技術價值不是「如何加減 Balance」，而是：

**如何證明每一塊錢從哪裡來、到哪裡去，而且任何時候都能把帳重新算回來。**
